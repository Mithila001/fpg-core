# E02 experiment family

E02A is a quick solver development workspace using prepared hint maps.

## Inputs and workflow

Select a database profile and choose 0 to 5 refinement rounds. The solver's
`initial` and `refinement_a`, post-processing and scoring settings supply the
stages. The submitted initial solve uses candidate hints and refinement uses an
existing-plan seed. E02A uses the shared refinement stage.
Its initial and refinement profiles prefer each room toward the vertical center
line using `room_center_line`; cluster horizontal centering is disabled and
the cluster front preference is disabled. Exterior-wall rules use unobstructed
outward paths, rather than requiring room walls to touch the generation boundary.
All three profiles contain explicit exposure rules; refinement executes `refinement_a`.

The configured refinement allows each room's position coordinates to change by up
to 20 project units and its dimensions by up to 10 units per round. The supplied `refinement_a` profile gives position and size equal
relative multipliers of 0.1. Use the `seed_stability` profile weight to adjust
the overall contribution. See the [solver contract](../../../docs/feature_documentations/floor_plan_solver.md#built-in-soft-constraints).
The other configured soft objectives and hard constraints remain active.
Repeated rounds apply the limits to each round's input plan.

The `initial`, `refinement_a`, and `refinement_b` entries in the canonical baseline each explicitly configure the same exposure policies:

| Constraint | Rule |
| --- | --- |
| Hard `exterior_wall_exposure` / `back_exposure` rule | At least one hallway or kitchen has 10 continuous units exposed at the back. |
| Hard `exterior_wall_exposure` / `garage_placement` rule | Every garage has a fully exposed front and either a fully exposed left or right wall. |
| Hard `exterior_wall_exposure` / `veranda_front` rule | Every veranda has a fully exposed front. |
| Hard `living_room_front` | Every living room has a fully exposed front when no veranda is supplied. |
| Soft `exterior_wall_exposure` / `kitchen_back_exposure` rule | At least one kitchen has 10 continuous units exposed at the back; violation weight 10. |

These are project units, not metres. Edit each intended profile separately; only `initial` and `refinement_a` execute in the E02A workflow. The [Core solver contract](../../../docs/feature_documentations/floor_plan_solver.md) explains rule syntax, validation, and migration, and the [design note](../../../docs/features/solver.md#exterior-wall-exposure-design-rationale) explains the geometry and its limits.

Each of the three profiles also configures `fully_shared_wall` with the same
rules. Every selected group consists of adjacent sides.

| Room types | Minimum sides | Combined uncovered tolerance in project units |
| --- | ---: | ---: |
| Bedroom, bathroom, attached bathroom, dining room, kitchen, hallway | 2 | 0 |
| Living room when a veranda is supplied | 3 | 0 |
| Living room when no veranda is supplied | 2 | 0 |
| Veranda | 1 | 0 |
| Garage | 2 | 10 |

The experiment checks whether these requirements promote compact layouts.
The garage allowance is an experimental value. The rules can make layouts
harder to find within the configured time limits. Check the solver status in
Diagnostics. `UNKNOWN` means the solver stopped without finding a plan or
proving infeasibility. Shared walls are enforced during the solver stages and
can change during post-processing. See [Fully shared walls](../../../docs/feature_documentations/floor_plan_solver.md#fully-shared-walls)
for coverage, conditions, and tolerance semantics.

After adding a Core constraint, add its key and settings to the desired solver
profile. Core validates constraint keys and settings. Lab's strict configuration
codec maps the saved profile to Core public types; if a new Core configuration field is
not yet represented in the codec, extend the corresponding Lab model and mapping
before using it. Unknown fields are rejected rather than silently dropped. Check
the applied solver snapshot on the Diagnostics view after a run.

Add the four user-supplied cleaned maps to
`fpg-lab/experiments/e02a/hint_maps.json` as a JSON object whose keys are unique
names and whose values are complete version-1 P01A/P01B portable exports. Copy
each cleaned candidate together with its matching generation specification,
request, units and room identities. The current file contains three maps. A
single map can be run as soon as it is available; **All maps**
requires exactly four. Project units must match the configuration.

Start Lab, open E-02-A, choose a map or all maps, validate and start. Each case
independently runs initial generation, one or more refinement rounds,
post-processing and final scoring. Openings are not generated. Inspect the
canvas by case and stage; Scores and Diagnostics show scoring and provenance.
Use **Copy floor plan** on any available Initial, Refinement or Post-process
stage to send its selected geometry and matching specification to E02B.
The **Post-process** canvas overlays detected inward recesses, their entrance
lines, and violating sections. Scores includes the measured geometry and room
contacts. For saved configurations, replace the old `maximum_length` setting
using the [Core scoring contract](../../../docs/feature_documentations/floor_plan_scoring.md#inward-recesses).

Failures stop the affected case and are recorded without stopping later cases.
Termination is cooperative between Core stages. The result page's **Retry run**
creates a new run from the selected maps, configuration, and refinement count
saved with that run, using the submitted profile snapshot.

Runs use separate database records and snapshot selected inputs, normalized
configuration, configuration hash, Core version, and effective solver profiles.
Later profile edits do not change a saved run. The background queue and startup
recovery follow Lab's single-process-per-database convention. Setup and result
pages use the shared desktop workspace; results remain available in history.

## Verification

From `fpg-lab/`, run `.venv/Scripts/python -m pytest tests/test_e02a.py -q`
and `.venv/Scripts/python -m scripts.verify_fpg_core`. Use a separate database
for manual checks alongside a running Lab. With a real supplied map, start one
bounded run and inspect each stage, score, diagnostics and termination. Solver
exposure describes geometry before post-processing, which may change room walls.

## E02B final floor-plan evaluation inspector

E02B investigates how the [Core scoring pipeline](../../../docs/feature_documentations/floor_plan_scoring.md)
measures geometry and applies rules. Copy a stage in E02A, paste it into E02B,
open **Import**, paste the JSON and choose **Preview**. Structural validation checks compatibility
with the generation specification. Overlaps, recesses, voids and other geometric
defects remain available for evaluation. Start from the temporary import or save
it by name and select it from **Saved floor plans**.

### Portable floor plans

The `fpg-floor-plan` schema, version `1`, contains these fields.

| Field | Content |
| --- | --- |
| `schema`, `version` | Format name and integer version. |
| `floor_plan` | Core `FloorPlan` geometry with floor and room polygon points, room IDs, types, names and identity redirects. Export retains room metadata and transformations where present. Openings are optional and scoring ignores them. |
| `specification` | Matching Core `FloorPlanGenerationSpec` with floor dimensions, room-size ranges and room relationships. |
| `project_units_per_meter` | Positive integer defining the source scale. Geometry and scoring settings use project units. E02B preserves the scale and coordinates in the document. |
| `source` | JSON object. E02A records the experiment, run ID, case, stage and Core version. |

### Configuration and execution

Select a database profile and open **Scoring settings**. The editor controls its scoring groups, evaluator
weights, enabled states, thresholds and settings. Validate a draft before
saving. Save applies the scoring section to the shared profile and rejects a
stale draft. Submitting a run captures the selected profile's saved scoring.

The official path calls Core in DEBUG and reports its actual gate, raw scores,
weights and contributions. When a critical evaluator fails its threshold, Core
marks downstream evaluations skipped. The independent path attempts those
evaluators with valid inputs and records each attempt separately. A diagnostic
score is an evaluator measurement with no official contribution. The result
shows skipped, disabled, inapplicable, unavailable and failed states explicitly.

### Reading the results

| View | How to inspect it |
| --- | --- |
| Overview | Read the official total and gate status in the sidebar. The chart and tables show earned contributions, raw scores, configured weights and thresholds. Independent attempts have their own table. |
| Geometry integrity | Select a finding to highlight its affected rooms and measured geometry. Diagonal segments, overlap footprints and areas outside the boundary use red overlays. |
| Required adjacency | Select an individual pair to see the measured shared wall and the required length. Solid green and dotted red centroid links show pair outcomes. The sidebar identifies the full AND/OR result. |
| Enclosed voids | Inspect actual void polygons, their areas, tolerance and scoring impact. Amber marks tolerated voids. |
| Inward recesses | Select a recess or section to inspect depth, width, ratio, nesting, branch count, parent sections and violation reasons. Arrows show sweep directions. Toggle entrances, sections, branch links or contributing room boundaries independently. |
| Room size consistency | Read measured room area labels and compare configured, actual and feasibility-adjusted limits in the rule matrix. Select a rule to highlight the participating rooms and inspect its penalty. |
| Kitchen–dining proximity | Select a pair to inspect its centroids, distance and shared wall. The sidebar explains the applied rule and reports both extrema across the evaluated pairs. |

Named layouts live in `fpg_e02b_saved_plan`. Runs in `fpg_e02b_run` retain the
submitted input and specification, normalized configuration and hash, Core
version, official and independent results with findings and geometry, execution
status, duration and errors. Deleting a saved layout or editing the settings does
not change that history. Startup marks abandoned jobs interrupted. Database changes use the explicit
[maintenance commands](../DEVELOPMENT.md#database-commands).

Run `python -m pytest tests/test_e02b.py -q` from `fpg-lab/` for the bounded
export, configuration, persistence, scoring and plotting checks. For desktop QA,
use the [UI verification sizes](../UI_STANDARDS.md#examples-and-review)
and an isolated database. Import the sample from the focused test, run it, switch
through each tab, and inspect an individual finding or measurement and its overlays.

E02A accepts optional initial solver time and random-seed overrides. Blank values
use the selected profile. The effective initial and refinement configurations are
saved with each run; retry uses the saved configuration and overrides.
