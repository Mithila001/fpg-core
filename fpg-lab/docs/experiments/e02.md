# E02 experiment family

E02A is a quick solver development workspace. P01B remains the standard saved
profile and preset experiment. E02A reads its configuration and cleaned hint maps
from its own files at submission; it never reads or changes saved system profiles
or P01B presets. Shared Core changes can affect both experiments.

## Inputs and workflow

Edit `fpg-lab/experiments/e02a/config.json`; `configuration` is the Lab schema 6
configuration document. Choose a refinement stage count from 0 to 5 on the setup
page; it defaults to 0 and is saved with each run. The solver's `initial` and `refinement_a` profiles, post-processing,
and floor-plan scoring sections supply the stages; their solver time limits and
hard and soft constraint lists are editable in the file. E02A requires candidate
hints for the initial solve and an existing-plan seed for refinement, overriding
those seed sources in the submitted configuration. All other configured solver
settings are retained. E02A does not use `experiments.p01b_refinement`.

After adding a Core constraint, add its key and settings to the desired solver
profile. Core validates constraint keys and settings. Lab's strict configuration
codec maps the file to Core public types; if a new Core configuration field is
not yet represented in the codec, extend the corresponding Lab model and mapping
before using it. Unknown fields are rejected rather than silently dropped. Check
the applied solver snapshot on the Diagnostics view after a run.

Add the four user-supplied cleaned maps to
`fpg-lab/experiments/e02a/hint_maps.json` as a JSON object whose keys are unique
names and whose values are complete version-1 P01A/P01B portable exports. Copy
each cleaned candidate together with its matching generation specification,
request, units and room identities. The file starts empty because no maps were
supplied. A single map can be run as soon as it is available; **All maps**
requires exactly four. Project units must match the configuration.

Start Lab, open E-02-A, choose a map or all maps, validate and start. Each case
independently runs initial generation, one or more refinement rounds,
post-processing and final scoring. Openings are not generated. Inspect the
canvas by case and stage; Scores and Diagnostics show scoring and provenance.
Failures stop the affected case and are recorded without stopping later cases.
Termination is cooperative between Core stages. The result page's **Retry run**
creates a new run from the selected maps, configuration, and refinement count
saved with that run, regardless of later file edits.

Runs use separate database records and snapshot selected inputs, normalized
configuration, configuration hash, Core version, and effective solver profiles.
Later file edits do not change a saved run. The background queue and startup
recovery follow Lab's single-process-per-database convention. Setup and result
pages use the shared desktop workspace; results remain available in history.

## Verification

From `fpg-lab/`, run `.venv/Scripts/python -m pytest tests/test_e02a.py -q`
and `.venv/Scripts/python -m scripts.verify_fpg_core`. Use a separate database
for manual checks alongside a running Lab. With a real supplied map, start one
bounded run and inspect each stage, score, diagnostics and termination. The
empty initial map file cannot establish end-to-end solver behavior.
